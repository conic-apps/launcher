# Linux packaging payload

Everything the Linux packages install that is **not** the executable itself:
the desktop entry and the icon set. All four consumers read from this one
directory, so nothing here is duplicated per format.

| Consumer                                                | Reads                                        |
| ------------------------------------------------------- | -------------------------------------------- |
| `cargo deb` — `app/Cargo.toml` `[package.metadata.deb]`  | `assets` below, relative to `app/`           |
| `cargo rpm` — `app/Cargo.toml` `[package.metadata.rpm]`  | the staged copy under `app/.rpm/`            |
| AppDir layout — `tools/package-linux.sh`                 | the same two, laid out under `AppDir/`       |
| `packaging/arch/PKGBUILD`                                | `package()`, relative to the repo root       |

`cargo rpm` is the odd one out: it only reads extra files from a staging
directory it calls `.rpm/` next to the crate's `Cargo.toml`, not from arbitrary
paths. `tools/package-linux.sh` populates `app/.rpm/usr/` from here before it
runs, so this directory stays the single source of truth. The spec sitting next to
that staging tree, `app/.rpm/conic-launcher.spec`, **is** committed — `cargo rpm`
reads it rather than generating one, and its `%files` section is the only place
that says which of these paths the rpm owns.

## `icons/`

**Committed, and regenerated by `tools/generate-icons.py`** — not produced at
package time. `dpkg-deb`, `rpmbuild` and `makepkg` all run on machines with
neither Python nor Pillow, so a package that could only be built where the
generator runs is not a package.

The set is the freedesktop hicolor ladder (`16x16` … `512x512`, plus
`scalable.svg`) at `usr/share/icons/hicolor/<size>/apps/conic-launcher.<ext>`.
Anything outside that ladder is never looked up by an icon theme, so there is no
reason to add a tenth raster.

The master artwork is `app/ui/assets/logo.png`; the scalable entry is
`app/ui/assets/images/logo-flat.svg`. Both are read in place, never copied into
the app tree — the package payload is the only copy.

## Naming

Every file is installed as **`conic-launcher`**, whatever its size. `16x16.png`
becomes `…/apps/conic-launcher.png`, not `…/apps/16x16.png`: that is the name
`Icon=conic-launcher` in the desktop entry resolves against, and it is also the
glob `app/.rpm/conic-launcher.spec` matches `%files` with. Renaming the installed
files breaks both at once, silently — the packages install and the launcher has
no icon.

## `conic-launcher.desktop`

The desktop entry, installed to
`/usr/share/applications/conic-launcher.desktop`. `Exec=conic-launcher %U` and
`Icon=conic-launcher` are both load-bearing:

- `Icon=conic-launcher` only resolves because the icon is installed under
  `…/apps/conic-launcher.png`. Renaming the installed files without editing this
  line leaves the package installed with an invisible launcher.
- `%U` is what registers `conic-launcher://` as a handled URL scheme (the
  `MimeType` line). Dropping it keeps the entry but silently removes the deep
  link.
- `StartupWMClass=conic-launcher` matches the WM_CLASS the winit backend reports,
  which is the executable name.

Validate changes with `desktop-file-validate` (the `desktop-file-utils`
package); `packaging/arch/PKGBUILD` runs it in its `check()` and CI runs it too.
